ATTACK 1 [FATAL] Dynamic sequence length scrubber is disconnected from warp matrix visualization and hardware fault simulation
Where: `frontend/src/components/ExecutiveCommandBar.jsx` (Lines 189-190, 321-324) and `frontend/src/components/HopperDieTopology.jsx` / `WarpVisualizer.jsx`
Problem: Requirement 5 demands an "Interactive Proving Ground: Must allow interactive parameter adjustment (dynamic sequence length scrubber, hardware target switcher, workload presets) and live execution proving loops." In a006's implementation, `seqLen` is passed into `ExecutiveCommandBar` where it renders a slider and computes `isRagged = seqLen % 32 !== 0`. However, `seqLen` is never passed into `WarpVisualizer.jsx` or `HopperDieTopology.jsx`. In `WarpVisualizer.jsx`, the active/boundary thread calculation hardcodes `boundaryLimit = isSwiglu ? 17 : (isRmsnorm ? 24 : 20)`. If the user moves the scrubber from 1023 (tail 31 threads) to any other value—such as an aligned length (e.g. 1024, remainder 0) or a length with tail 5—the warp lane matrix remains frozen at lane 17. The user scrubbing the slider causes zero change to warp lanes, predicate mask registers (`@p0`), or memory address bounds, making the dynamic parameter adjustment completely non-functional as a hardware proving ground.

ATTACK 3 [MAJOR] Hardware target switcher fails to update architecture-specific topology or PTX disassembly
Where: `frontend/src/components/HopperDieTopology.jsx` (Lines 342, 355) and `frontend/src/components/SiliconMemoryWaterfall.jsx` (Lines 418, 458)
Problem: Requirement 4 & 5 require authentic representation across NVIDIA Hopper H100 and Blackwell B200 hardware targets ("demonstrates closed-loop Nemotron Red Adversary fuzzer vs Nemotron Blue Triton healer on NVIDIA Hopper H100 and Blackwell B200 hardware"). When the user selects "NVIDIA Blackwell B200" in the cockpit dropdown:
1. `HopperDieTopology` hardcodes `TOTAL_SMS = 132` (Hopper GH100 count) and displays static title "NVIDIA GH100 SILICON DIE TOPOLOGY - 132 SMs · 8 GPCs · TSMC 4N". It does not adapt to Blackwell B200's 160 SMs (or dual-die 148/160 SM layout).
2. `SiliconMemoryWaterfall` statically titles the instrument "HOPPER H100 SILICON MEMORY HIERARCHY WATERFALL" and hardcodes "SM_90a Architecture" even when B200 (SM_100, 8.0 TB/s HBM3e) or Ada L40S (SM_89, 864 GB/s GDDR6) is selected. Switching hardware targets changes superficial text in Nsight HUD while the physical die and memory hierarchy remain completely Hopper-locked.

ATTACK 4 [MAJOR] Hardcoded faulting SM index 14 breaks multi-workload execution authenticity
Where: `frontend/src/components/HopperDieTopology.jsx` (Lines 343, 379-386)
Problem: `HopperDieTopology` hardcodes `const FAULTING_SM = 14`. Whether the operator executes SwiGLU (SIGSEGV 139), RMSNorm (Silent SDC), or Softmax (NaN Overflow), and regardless of any live backend telemetry or different seed/iteration, SM 14 is hardcoded as the sole failing core. If the user clicks any other SM node in the 132-SM grid (e.g. SM 42 or SM 88), `selectedSm` changes, but fault generation and MMU page trap animations remain permanently anchored to SM 14. The component provides no dynamic mapping between backend fuzzer fault reports and silicon core addresses.
